# U05 — Adopter Yia dans un dépôt existant

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Inventorier avant d'ajouter

Avant toute écriture, relever l'état du dépôt et sauvegarder les fichiers
humains existants dans Git :

```bash
git status --short
git diff -- Makefile .env.example AGENTS.md .agents
git ls-files Makefile .env.example AGENTS.md '.agents/**'
```

Commiter ou remiser séparément les changements locaux utiles avant de commencer
l'adoption, afin que le diff produit par Yia reste attribuable et réversible.

Ajouter ensuite le sous-module comme dans U03 et créer un `yia.yml` qui décrit
l'état cible réel. Ne pas copier aveuglément les templates par-dessus des
fichiers existants. Si le Makefile contient déjà des cibles métier, lui ajouter
manuellement le proxy générique sans supprimer ces cibles :

```makefile
%:
	@$(MAKE) --no-print-directory -C .yia PROJECT_ROOT="$(CURDIR)" $@
```

Exécuter `make init`, puis examiner le diff avant `make update` :

```bash
make init
git diff -- Makefile .env.example AGENTS.md .agents
make validate
make update
make update
git status --short
```

Yia crée `Makefile`, `.env.example` et `.env` seulement lorsqu'ils sont absents.
Il conserve les valeurs locales de `.env`, le code applicatif et le contenu
humain hors des sections documentaires gérées. Si une fusion sûre n'est pas
possible, conserver le fichier du projet, résoudre le conflit explicitement et
relancer la validation. Aucun fichier humain ne doit être remplacé uniquement
pour faire disparaître l'erreur.

# U03 — Ajouter Yia à un nouveau dépôt

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Créer et épingler le sous-module

```bash
mkdir full
cd full
git init
git submodule add "<URL-DU-DÉPÔT-YIA>" .yia
git -C .yia checkout "<COMMIT-YIA-VALIDÉ>"
cp .yia/templates/project/Makefile ./Makefile
```

Les valeurs entre chevrons doivent être remplacées par l'URL autorisée et le
commit choisi par l'équipe. Le dépôt parent versionne `.gitmodules` et le
gitlink `.yia` : il épingle ainsi Yia, même si la branche distante évolue.
Ne jamais écrire de configuration ou de donnée propre au projet dans `.yia/`.

Créer ensuite à la racine `yia.yml`, `.env.example` et `.gitignore`. Pour une
première prise en main sans Docker, utiliser les contenus de [U06](./u06.md). Pour
le projet full stack de référence, utiliser ceux de [U24](./u24.md).

## Préparer le premier commit

Contrôler le sous-module, les prérequis et la configuration avant de publier le
projet :

```bash
git submodule status .yia
make check-install
make validate
git status --short --ignored
```

Le fichier `.gitignore` doit au minimum exclure `.env`, `.yia-runtime/` et
`.yia-data/`. Vérifier qu'aucun secret, token, mot de passe ou fichier local ne
sera versionné. `.env.example` ne contient que les noms de variables et des
valeurs d'exemple non sensibles.

Préparer ensuite le commit initial. L'ajout explicite évite d'inclure par
accident un fichier local qui ne serait pas encore ignoré :

```bash
git branch -M main
git add .gitmodules .yia .gitignore .env.example Makefile yia.yml
git diff --cached --check
git diff --cached --name-only
```

Si le projet contient des sources sous `apps/`, les examiner puis les ajouter
séparément :

```bash
git add apps
git diff --cached --name-only
```

Créer le commit seulement après la dernière vérification :

```bash
git diff --cached --check
git commit -m "Initialize project with Yia"
```

Le dépôt parent enregistre un gitlink pour `.yia`, pas une copie des fichiers du
sous-module.

## Créer le dépôt sur GitHub

Dans l'[interface de création GitHub](https://github.com/new) :

1. choisir le compte personnel ou l'organisation propriétaire ;
2. saisir `full` comme nom du dépôt ;
3. choisir la visibilité privée, publique ou interne autorisée par l'équipe ;
4. ne pas ajouter de README, de `.gitignore` ni de licence, puisque le dépôt
   local possède déjà son premier commit ;
5. créer le dépôt puis copier son URL SSH ou HTTPS depuis la page « Quick setup ».

Laisser le dépôt distant vide évite de créer un historique concurrent avant le
premier push. La procédure officielle est détaillée dans
[la documentation GitHub](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github).

## Relier le dépôt local et pousser le code

Avec une URL SSH :

```bash
git remote add origin "git@github.com:<PROPRIÉTAIRE>/full.git"
git remote -v
git push -u origin main
```

Avec HTTPS, remplacer l'URL par :

```text
https://github.com/<PROPRIÉTAIRE>/full.git
```

L'authentification doit utiliser la clé SSH, le gestionnaire d'identifiants ou
le mécanisme GitHub autorisé par l'équipe. Ne jamais inscrire un token dans
l'URL, un script ou un fichier versionné.

Vérifier le résultat local et distant :

```bash
git status --short
git branch -vv
git remote get-url origin
git ls-remote --heads origin main
```

`git status --short` ne doit rien afficher. La branche `main` doit suivre
`origin/main`, et `git ls-remote` doit retourner la référence distante.

Si un remote `origin` existe déjà, l'inspecter avec `git remote -v`. N'utiliser
`git remote set-url origin "<NOUVELLE-URL>"` qu'après avoir confirmé qu'il cible
le mauvais dépôt. Si le dépôt GitHub a été initialisé par erreur avec un commit,
ne pas forcer le push : recréer un dépôt distant vide ou réconcilier explicitement
les deux historiques.

## Variante avec GitHub CLI

Lorsque `gh` est installé et authentifié, GitHub CLI peut créer le dépôt,
ajouter `origin` et pousser le commit courant en une commande :

```bash
gh auth status
gh repo create "<PROPRIÉTAIRE>/full" \
  --private \
  --source=. \
  --remote=origin \
  --push
```

Remplacer `--private` par `--public` ou `--internal` selon la politique de
l'équipe. Cette variante suppose que le commit initial existe déjà. Les options
sont décrites dans le
[manuel de `gh repo create`](https://cli.github.com/manual/gh_repo_create).

## Cloner ensuite le projet

Cloner ultérieurement le dépôt consommateur avec ses sous-modules :

```bash
git clone --recurse-submodules "<URL-DU-PROJET>"
```

ou, après un clone ordinaire :

```bash
git submodule update --init --recursive
```

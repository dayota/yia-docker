# U25 — Construire un monorepo multi-applications

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Objectif

Faire converger un même projet contenant :

- une API Laravel sous PHP 8.4 sur `api.monorepo.localhost` ;
- une application Symfony historique sous PHP 8.2 sur
  `legacy.monorepo.localhost` ;
- un frontend Nuxt sous Node 24 sur `monorepo.localhost` ;
- une interface d'administration Nuxt sous Node 22 sur
  `admin.monorepo.localhost` ;
- une instance PostgreSQL 18 privée partagée par les applications qui en ont
  besoin.

Les applications partageant une version de PHP partageraient son service FPM.
Ici, les deux versions produisent deux services distincts. Chaque application
Node possède toujours son propre processus et son propre volume
`node_modules`, même si plusieurs applications utilisent la même version.

## Arborescence

```text
monorepo/
├── .yia/
├── .env.example
├── .gitignore
├── Makefile
├── yia.yml
└── apps/
    ├── admin/
    │   ├── package.json
    │   └── server.mjs
    ├── api/
    │   └── public/index.php
    ├── frontend/
    │   ├── package.json
    │   └── server.mjs
    └── legacy/
        └── public/index.php
```

Réutiliser le `Makefile`, `.gitignore`, `.env.example` et `.env` de U24. Les
sondes PHP et Node ont la même structure que celles de U24 ; seules leurs
réponses permettent d'identifier l'application :

```text
Yia PHP fixture: api
Yia PHP fixture: legacy
Yia Node fixture: frontend
Yia Node fixture: admin
```

Les deux `package.json` contiennent le script
`"dev": "node server.mjs"`. Les deux fichiers `server.mjs` acceptent les
options `--host` et `--port` exactement comme celui de U24. Ces sondes sont
remplacées par les véritables sources Laravel, Symfony et Nuxt dans un projet
métier.

## Décrire l'état cible

```yaml
version: 1
project:
  name: monorepo
environment:
  domain: monorepo.localhost
services:
  postgres:
    enabled: true
    version: "18"
applications:
  api:
    type: php
    path: apps/api
    runtime:
      php: "8.4"
    framework:
      name: laravel
      version: 13
    web:
      hostname: api.monorepo.localhost
      public_directory: public
  legacy:
    type: php
    path: apps/legacy
    runtime:
      php: "8.2"
    framework:
      name: symfony
      version: "7.4"
    web:
      hostname: legacy.monorepo.localhost
      public_directory: public
  frontend:
    type: node
    path: apps/frontend
    runtime:
      node: "24"
    framework:
      name: nuxt
      version: 4
    web:
      hostname: monorepo.localhost
      port: 3000
  admin:
    type: node
    path: apps/admin
    runtime:
      node: "22"
    framework:
      name: nuxt
      version: 4
    web:
      hostname: admin.monorepo.localhost
      port: 3000
```

Le port `3000` est privé à chacun des deux containers Node et ne crée donc pas
de conflit. Apache sélectionne l'amont avec le hostname. PostgreSQL n'est pas
publié sur l'hôte ; son adresse sur le réseau Compose est `postgres:5432`.
Yia n'injecte pas automatiquement les variables de connexion dans les
applications : leur configuration métier reste sous la responsabilité du
projet.

## Faire converger et contrôler

Après avoir renseigné localement `POSTGRES_PASSWORD`, suivre le même démarrage
que U24 :

```bash
make init
make validate
make config
make update
```

Les services logiques attendus sont :

```text
apache
node-22-admin
node-24-frontend
php-8.2
php-8.4
postgres
```

Vérifier chaque route :

```bash
curl --fail --resolve api.monorepo.localhost:80:127.0.0.1 \
  http://api.monorepo.localhost/
curl --fail --resolve legacy.monorepo.localhost:80:127.0.0.1 \
  http://legacy.monorepo.localhost/
curl --fail --resolve monorepo.localhost:80:127.0.0.1 \
  http://monorepo.localhost/
curl --fail --resolve admin.monorepo.localhost:80:127.0.0.1 \
  http://admin.monorepo.localhost/
make exec SERVICE=postgres \
  CMD="psql -U yia_app -d yia_app -tAc 'SELECT 1'"
make ps FORMAT=json
make doctor FORMAT=json
```

Les quatre réponses HTTP doivent identifier la bonne application, PostgreSQL
doit retourner `1`, les six services doivent être `running` et leurs
healthchecks `healthy`. Deux nouveaux `make update` doivent laisser les six
containers et tous les volumes en place. Les commandes de nettoyage et leurs
garanties sont identiques à U24. Consulter [T01](./t01.md), [T02](./t02.md) ou
[T05](./t05.md) selon que l'échec concerne Docker, le routage ou les artefacts
générés.

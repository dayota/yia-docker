# U62 — Publier une nouvelle version de Yia

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md) · [U52 — Mettre à jour un projet consommateur](./u52.md)

## Objectif et périmètre

Ce parcours s'adresse au mainteneur qui développe **dans le dépôt du moteur
Yia**. Il publie un commit et un tag Git immuable afin que les projets
consommateurs puissent épingler leur sous-module `.yia/` sur cette version.
Il ne publie ni paquet PyPI ni image Docker dans un registre : aucune cible
Make ou automatisation de dépôt ne garantit aujourd'hui ces opérations.

L'exemple utilise `0.2.0` et `v0.2.0` uniquement pour illustrer les
commandes. Choisir la version réelle avant de les appliquer. Le projet Yia
ne possède pas de `yia.yml` à modifier pour sa propre publication, ni de
`.env.example` ou d'application de démonstration à créer pour cette étape.

## 1. Préparer la version

Travailler sur la branche destinée à la publication. Vérifier les changements
et l'identité du dépôt distant **avant tout push** :

```bash
git status --short
git branch --show-current
git remote -v
git tag --list 'v0.2.0'
git ls-remote --tags origin v0.2.0
```

Les deux dernières commandes ne doivent afficher aucun tag existant, local
ou distant. Adapter `origin` au dépôt de publication réellement choisi.
Examiner les changements depuis le
dernier tag publié et décider du numéro selon leur compatibilité. Une rupture
du format `yia.yml` exige aussi une nouvelle version de schéma et une
procédure de migration documentée ; le numéro du moteur et celui du schéma
sont deux choses distinctes. Ne pas publier de secret ni de données locales.

Mettre à jour **les deux** valeurs de version du moteur, sans changer les
versions de schémas si leurs contrats n'ont pas évolué :

```text
src/yia/versions.py     YIA_VERSION = "0.2.0"
pyproject.toml          [project].version = "0.2.0"
```

Adapter aussi les spécifications, les cas d'usage, les tests et les notes de
version à la fonctionnalité publiée. Aucun fichier `CHANGELOG` ni outil de
release automatique n'est actuellement imposé par le dépôt ; préparer les
notes destinées à la publication Git selon le canal choisi.

## 2. Vérifier la candidate

Depuis la racine du dépôt Yia :

```bash
git diff --check
make version FORMAT=json
make test
make validate CONFIG=tests/projects/minimal/yia.yml
make validate CONFIG=tests/projects/v2-managed/yia.yml
```

`make version` doit afficher la même version du moteur que
`pyproject.toml`. `make test` exécute la suite automatisée, dont le contrôle
de cohérence des versions et la présence des ressources distribuées. Les
tests Docker sont opt-in : si la version modifie les images, les volumes, le
routage ou le cycle de vie, exécuter aussi les scénarios d'intégration avec
un daemon Docker disponible, selon le [README](../../README.md). Vérifier
`make doctor` sur un **projet consommateur initialisé** représentatif, pas à
la racine du dépôt Yia où aucun `yia.yml` de projet n'est attendu.

Relire enfin le diff complet, les fichiers non suivis et les éventuelles
migrations. Ne pas créer le tag tant qu'un contrôle requis échoue.

## 3. Enregistrer puis publier le commit

Indexer seulement les fichiers relus, créer le commit de release et vérifier
que la copie de travail est propre. Les commandes suivantes restent un
**exemple pour `0.2.0`** :

```bash
git diff --cached --check
git commit -m "Release Yia 0.2.0"
git status --short
git show --no-patch --format=fuller HEAD
git tag -a v0.2.0 -m "Yia 0.2.0"
git rev-parse HEAD
git rev-parse 'v0.2.0^{commit}'
```

Les deux derniers identifiants de commit doivent être égaux. Le commit
suppose que les fichiers souhaités ont été indexés après revue (`git add -p`
ou sélection explicite) ; ne pas utiliser `git add -A` sans inspecter les
fichiers. Ne pas déplacer ou recréer un tag déjà publié.

Après confirmation du dépôt distant et de la branche cibles, publier le
commit, attendre les contrôles éventuels de ce dépôt, puis publier le tag :

```bash
git push origin HEAD
git push origin v0.2.0
git ls-remote --tags origin v0.2.0
```

Remplacer `origin` si ce n'est pas le dépôt de publication prévu. Le résultat
observable est un tag distant `v0.2.0` pointant sur le commit validé ; aucun
container, volume ni projet consommateur n'est modifié par ces commandes.
En cas de défaut découvert **après** publication, corriger dans un nouveau
commit et publier une nouvelle version : ne pas réécrire le tag distant.

## 4. Vérifier l'adoption par un projet consommateur

La publication ne met pas automatiquement à jour les sous-modules des
projets. Dans un projet de test, suivre [U52](./u52.md) pour épingler
explicitement `.yia/` sur le commit publié, contrôler la migration éventuelle,
puis exécuter `make version`, `make validate`, `make update` deux fois et
`make doctor`. Le nettoyage du projet de test suit ses propres règles de
persistance ; la publication Git elle-même ne nécessite aucune suppression.

# U64 — Initialiser et déverrouiller OpenBao persistant

OpenBao fournit un coffre de secrets local persistant, accessible uniquement
depuis le réseau Docker. Ce scénario n'est pas un déploiement de production :
une seule instance Raft, sans TLS ni haute disponibilité.

## Projet minimal

```text
coffre/
├── .yia/              # sous-module Yia en lecture seule
└── yia.yml
```

```yaml
version: 2
project:
  name: coffre
environment:
  domain: coffre.localhost
services:
  openbao:
    version: "2.5.0"
applications: {}
```

Aucun token ni clé n'est attendu dans `.env` ou `yia.yml`.
La fixture correspondante est `tests/projects/openbao/yia.yml`.

## Étapes

1. Initialiser le projet et contrôler la configuration :

   ```bash
   make -f .yia/Makefile init
   make validate
   make update
   ```

   Le premier `update` démarre le conteneur mais échoue avec
   `YIA_OPENBAO_NOT_READY` et l'état `uninitialized`. C'est attendu.

2. Ouvrir un shell, puis initialiser explicitement le coffre :

   ```bash
   make shell SERVICE=openbao
   bao operator init
   ```

   Cette commande interactive affiche les clés de déverrouillage et le token
   administrateur initial. Les conserver immédiatement dans un stockage sûr
   hors du projet et de Yia. Ne pas copier cette sortie dans un ticket, une
   fixture, la documentation, `.env` ou un journal de CI.

3. Dans ce shell, déverrouiller le coffre :

   ```bash
   bao operator unseal
   ```

   Saisir une clé au prompt, sans la placer dans les arguments de commande.
   Répéter avec des clés distinctes jusqu'au seuil indiqué à l'initialisation
   (par défaut trois clés sur cinq). Vérifier puis quitter :

   ```bash
   bao status
   exit
   ```

4. Relancer les contrôles depuis le projet :

   ```bash
   make update
   make status FORMAT=json
   make doctor FORMAT=json
   make update
   ```

   L'état OpenBao est `ready`, `initialized: true`, `sealed: false`.
   Le second `update` ne recrée pas le conteneur ni les fichiers inchangés.
   Les diagnostics ne contiennent pas de clé ni de token.

## Accès et persistance

Les applications du réseau Docker utilisent `http://openbao:8200` ; elles
doivent s'authentifier avec des droits adaptés. Aucun port n'est publié sur
l'hôte, et Apache ne route pas vers OpenBao. Yia ne distribue aucun token.

Les données Raft résident dans le volume nommé `openbao-data`. `down`,
`restart`, `rebuild`, `reset` et le retrait du service préservent ce volume.
Après redémarrage ou recréation, le coffre est verrouillé : les commandes de
convergence échouent avec l'état `sealed`. Répéter seulement le déverrouillage,
puis `make update` ; ne pas réinitialiser un coffre existant.

## Nettoyage et dépannage

```bash
make down
```

Cette commande conserve les données. Leur suppression volontaire, irréversible,
exige `make destroy-data YES=1` et concerne tous les volumes du projet.

Si le service reste indisponible, consulter `make logs SERVICE=openbao` et
`bao status` via le shell. Voir [T01](./t01.md) pour les dépendances Docker et
[T05](./t05.md) pour un runtime absent ou obsolète. Ne pas publier de secrets
dans les logs ou les sorties de diagnostic.

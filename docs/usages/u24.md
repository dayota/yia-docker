# U24 — Construire un projet full stack avec PostgreSQL

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Objectif

Construire un environnement de développement local réunissant :

- une API PHP 8.4 exposée sur `api.full.localhost` ;
- un frontend Node 24 exposé sur `full.localhost` ;
- PostgreSQL 18 sur le réseau privé du projet ;
- Apache comme unique point d'entrée HTTP sur le port 80 ;
- des volumes séparés pour PostgreSQL, `vendor/` et `node_modules/`.

Cet exemple vérifie l'infrastructure Yia avec deux applications minimales. Les
champs `laravel` et `nuxt` décrivent les frameworks des applications réelles,
mais Yia ne crée ni un projet Laravel ni un projet Nuxt. Dans un produit, les
répertoires `apps/api` et `apps/frontend` contiennent les sources complètes de
ces frameworks. Les sondes ci-dessous permettent de reproduire le routage sans
ajouter leurs générateurs ou leur code métier au périmètre du guide.

## Prérequis

- Git, Make, Python 3.12 ou supérieur, Docker et Docker Compose sont installés ;
- le daemon Docker est accessible sans `sudo` pour les commandes courantes ;
- le port 80 de l'hôte est libre ;
- Yia 0.1.0 est présent comme sous-module Git dans `.yia/` ;
- les commandes sont exécutées depuis la racine du projet consommateur.

Utiliser `make check-install` pour contrôler les outils. En cas d'échec Docker
ou de healthcheck, consulter [T01](./t01.md). Pour un conflit de port ou de hostname,
consulter [T02](./t02.md).

## Arborescence initiale

```text
full/
├── .yia/                         # sous-module Git Yia, en lecture seule
├── .env.example
├── .gitignore
├── Makefile
├── yia.yml
└── apps/
    ├── api/
    │   └── public/
    │       └── index.php
    └── frontend/
        ├── package.json
        └── server.mjs
```

Le fichier `.env` sera créé localement avant l'initialisation. Il ne doit pas
être versionné.

## Fichiers du projet

`Makefile` délègue toute la logique au sous-module Yia :

```makefile
%:
	@$(MAKE) --no-print-directory -C .yia PROJECT_ROOT="$(CURDIR)" $@
```

`.gitignore` exclut uniquement les données locales et les artefacts
reconstructibles de cet exemple :

```gitignore
.env
.yia-runtime/
.yia-data/
```

`.env.example` documente les variables attendues sans valeur sensible :

```dotenv
# Obligatoire lorsque PostgreSQL est activé.
POSTGRES_PASSWORD=

# Appliquées uniquement à l'initialisation d'un volume PostgreSQL vide.
POSTGRES_USER=yia_app
POSTGRES_DB=yia_app
```

`yia.yml` décrit l'état cible complet :

```yaml
version: 1
project:
  name: full
environment:
  domain: full.localhost
services:
  postgres:
    enabled: true
    version: "18"
applications:
  api:
    type: php
    path: apps/api
    runtime:
      php: "8.4"
    framework:
      name: laravel
      version: 13
    web:
      hostname: api.full.localhost
      public_directory: public
  frontend:
    type: node
    path: apps/frontend
    runtime:
      node: "24"
    framework:
      name: nuxt
      version: 4
    web:
      hostname: full.localhost
      port: 3000
```

L'API minimale `apps/api/public/index.php` confirme le passage par Apache et
PHP-FPM :

```php
<?php

header('Content-Type: text/plain');
echo "Yia PHP fixture: api\n";
```

Le frontend minimal `apps/frontend/package.json` fournit le script `dev` attendu
par Yia. L'absence de `package_manager` dans `yia.yml` sélectionne pnpm par
défaut :

```json
{
  "private": true,
  "scripts": {
    "dev": "node server.mjs"
  }
}
```

`apps/frontend/server.mjs` accepte les options `--host` et `--port` transmises
par le runtime Node :

```javascript
import { createServer } from "node:http";

const arguments_ = process.argv.slice(2);

function option(name, fallback) {
  const index = arguments_.indexOf(name);
  return index >= 0 && arguments_[index + 1] ? arguments_[index + 1] : fallback;
}

const host = option("--host", "127.0.0.1");
const port = Number(option("--port", "3000"));

createServer((_request, response) => {
  response.writeHead(200, { "content-type": "text/plain" });
  response.end("Yia Node fixture: frontend\n");
}).listen(port, host);
```

## Préparer les variables locales

Créer `.env` depuis le modèle puis renseigner un mot de passe local non vide :

```bash
cp .env.example .env
```

Le contenu attendu est le suivant ; la valeur entre chevrons doit être
remplacée localement et ne doit jamais être commitée :

```dotenv
POSTGRES_PASSWORD=<mot-de-passe-local-non-versionné>
POSTGRES_USER=yia_app
POSTGRES_DB=yia_app
```

Ces valeurs initialisent uniquement un volume PostgreSQL vide. Les changer
ensuite ne migre pas automatiquement une base existante.

## Initialiser et démarrer

```bash
make init
make validate
make config
make update
```

`make init` installe le système documentaire et génère `.yia-runtime/` sans
démarrer de container. `make update` valide de nouveau l'état, synchronise la
documentation et le runtime, construit les images nécessaires puis attend les
healthchecks.

Les services logiques attendus sont :

```text
apache
node-24-frontend
php-8.4
postgres
```

## Vérifier le résultat

Contrôler les deux routes HTTP en forçant explicitement leur résolution locale :

```bash
curl --fail --resolve api.full.localhost:80:127.0.0.1 \
  http://api.full.localhost/
curl --fail --resolve full.localhost:80:127.0.0.1 \
  http://full.localhost/
```

Les réponses attendues sont :

```text
Yia PHP fixture: api
Yia Node fixture: frontend
```

Vérifier PostgreSQL depuis son service logique :

```bash
make exec SERVICE=postgres \
  CMD="psql -U yia_app -d yia_app -tAc 'SELECT 1'"
```

La commande doit retourner `1`. Observer ensuite l'environnement avec les
sorties machine stables :

```bash
make ps FORMAT=json
make status FORMAT=json
make doctor FORMAT=json
make test
```

`ps` doit présenter les quatre services en état `running` et leurs healthchecks
en état `healthy`. `doctor` doit retourner un statut global `ok`.

## Artefacts attendus

Yia crée notamment :

```text
.agents/docs/architecture/development-environment.md
.agents/skills/project-docs/SKILL.md
.agents/skills/update-project-docs/SKILL.md
.yia-runtime/apache/vhosts.conf
.yia-runtime/compose/compose.yaml
.yia-runtime/php/8.4/fpm-pools.conf
.yia-runtime/state/generation-manifest.json
.yia-runtime/state/yia-state.json
```

Les fichiers de `.agents/` appartiennent au projet et peuvent être versionnés
selon leur contrat. `.yia-runtime/` est entièrement reconstructible et ne doit
jamais être modifié manuellement. Aucun de ces fichiers ne contient la valeur de
`POSTGRES_PASSWORD`.

## Vérifier l'idempotence

Sans modifier `yia.yml` ni les sources, exécuter deux nouvelles convergences :

```bash
make update
make update
```

Le runtime généré doit être annoncé comme déjà à jour. Les containers ne doivent
pas être recréés et les volumes PostgreSQL, `vendor` et `node_modules` doivent
être conservés. En cas de runtime absent ou obsolète, consulter [T05](./t05.md).

## Arrêter ou nettoyer

Pour arrêter l'environnement tout en conservant les données pour un prochain
démarrage :

```bash
make down
```

Pour supprimer les containers, le réseau et le runtime généré tout en conservant
les volumes persistants :

```bash
make destroy
```

La suppression des données est une opération distincte et volontaire :

```bash
make destroy-data
```

La dernière commande affiche les volumes ciblés et demande une confirmation.
Elle ne doit être utilisée que lorsque la perte des données PostgreSQL et des
volumes de dépendances du projet est acceptée.

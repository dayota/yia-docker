# U26 — Utiliser des sous-domaines `.localhost`

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Objectif

Comprendre et vérifier le routage utilisé dans U23, U24 et U25. Chaque bloc
`web` associe exactement un hostname à une application. Apache écoute seul sur
le port 80 et transmet la requête au service PHP-FPM ou Node approprié d'après
l'en-tête HTTP `Host`.

Les noms terminés par `.localhost` sont destinés au loopback. Sur un système qui
les résout conformément à cette convention, aucune entrée `/etc/hosts` n'est
nécessaire. La commande `--resolve` utilisée dans ce guide rend toutefois le
test déterministe sans modifier la configuration de la machine :

```bash
curl --fail --resolve api.full.localhost:80:127.0.0.1 \
  http://api.full.localhost/
```

Pour vérifier la résolution native de l'hôte séparément du routage Yia :

```bash
getent hosts full.localhost
getent hosts api.full.localhost
```

Si la résolution native échoue mais que `curl --resolve` fonctionne, les
containers et Apache sont opérationnels ; seul le résolveur de l'hôte reste à
configurer. Si `curl --resolve` atteint Apache mais retourne le mauvais site,
contrôler les valeurs `web.hostname`, puis exécuter :

```bash
make validate
make generate
make config
make restart
```

Ne pas ajouter un wildcard, plusieurs hostnames à une application, HTTPS ou un
autre port Apache : ces comportements ne font pas partie du contrat V1. Ne pas
arrêter non plus un processus externe occupant le port 80 sans accord explicite
de son propriétaire. Le diagnostic complet se trouve dans [T02](./t02.md).

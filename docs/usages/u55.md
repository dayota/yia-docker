# U55 — Ajouter, modifier ou supprimer un framework pris en charge par Yia

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Objectif

Faire évoluer, dans le dépôt Yia, le catalogue des frameworks acceptés dans
`yia.yml`. Ce cas s'adresse aux mainteneurs de Yia, pas aux projets
consommateurs : un projet consommateur ne modifie jamais son sous-module `.yia/`.

Dans l'implémentation actuelle, le nom du framework est une métadonnée déclarative :

- le schéma vérifie que le nom est connu et compatible avec le type `php` ou
  `node` ;
- le modèle normalisé et la documentation projet conservent cette information ;
- les générateurs Docker restent génériques et n'installent aucun framework.

Ajouter un nom au schéma ne suffit donc pas à promettre une installation, une
migration ou une commande propre à ce framework. Si une future prise en charge
exige un comportement de runtime particulier, ce comportement doit recevoir son
propre contrat, son implémentation et ses tests.

## Localiser le catalogue actuel

Les sources à examiner avant toute modification sont :

```text
docs/yia-spec.md
docs/configuration.md
schemas/yia.schema.json
src/yia/config/
src/yia/documentation/manager.py
tests/unit/test_schema.py
tests/unit/test_normalization.py
tests/unit/test_documentation.py
tests/projects/
docs/usages/
```

Le schéma possède deux niveaux complémentaires :

1. l'énumération globale `framework.name` contient `laravel`, `symfony` et
   `nuxt` ;
2. les contraintes par type n'acceptent que `laravel` et `symfony` pour PHP, et
   uniquement `nuxt` pour Node.

Toute évolution doit garder ces deux niveaux cohérents. Le champ
`framework.version` n'est pas un catalogue de versions supportées : il accepte
déjà toute chaîne non vide ou tout entier positif.

## Ajouter un framework

L'exemple suivant illustre l'ajout de `sveltekit` aux applications Node. Tant que
les modifications décrites ici ne sont pas intégrées, cette valeur reste
invalide dans Yia.

### 1. Définir le contrat avant le code

Documenter dans `docs/configuration.md` :

- l'identifiant stable `sveltekit` ;
- le type d'application autorisé, ici `node` ;
- le fait que le champ reste descriptif ;
- toute exigence supplémentaire éventuelle, qui ne doit pas être inventée à
  partir du seul nom du framework.

Mettre à jour les listes normatives et la Definition of Done qui énumèrent les
frameworks. Si la capacité modifie un invariant transversal, adapter également
`docs/yia-spec.md`.

### 2. Écrire les tests de contrat

Ajouter au minimum dans `tests/unit/test_schema.py` :

- une configuration Node avec `framework.name: sveltekit` acceptée ;
- la même valeur dans une application PHP rejetée avec
  `YIA_CONFIG_INVALID` ;
- un nom toujours inconnu rejeté.

Compléter `tests/unit/test_normalization.py` et
`tests/unit/test_documentation.py` pour vérifier que le nom et sa version sont
normalisés puis rendus dans la documentation dérivée.

Une fixture dédiée ou une fixture existante peut alors utiliser :

```yaml
version: 1
project:
  name: sveltekit-example
environment:
  domain: sveltekit-example.localhost
applications:
  frontend:
    type: node
    path: apps/frontend
    runtime:
      node: "24"
      package_manager: pnpm
    framework:
      name: sveltekit
      version: 2
    web:
      hostname: sveltekit-example.localhost
      port: 3000
```

La fixture Node doit aussi contenir un `package.json` valide avec un script
`dev`. Yia ne crée pas les sources SvelteKit.

### 3. Étendre le schéma

Dans `schemas/yia.schema.json`, ajouter `sveltekit` à l'énumération globale :

```diff
             "enum": [
               "laravel",
               "symfony",
-              "nuxt"
+              "nuxt",
+              "sveltekit"
             ]
```

La contrainte Node, actuellement exprimée par `const`, doit devenir une
énumération :

```diff
-            "const": "nuxt"
+            "enum": [
+              "nuxt",
+              "sveltekit"
+            ]
```

Ne pas ajouter `sveltekit` à l'énumération PHP. Une extension du catalogue est
compatible avec les anciennes configurations V1 ; elle ne réinterprète pas une
valeur auparavant valide.

### 4. Synchroniser les exemples

Mettre à jour les exemples et listes qui prétendent être exhaustifs dans :

- `docs/configuration.md` ;
- `docs/yia-spec.md` lorsqu'il énumère les capacités initiales ;
- `docs/usages-management.md` et les cas d'usage concernés ;
- les fixtures de `tests/projects/` retenues pour la non-régression.

Une simple occurrence historique de Laravel, Symfony ou Nuxt n'a pas à être
remplacée. Seules les listes contractuelles exhaustives et les exemples choisis
pour couvrir le nouveau framework doivent évoluer.

## Modifier un framework existant

### Modifier seulement une version applicative

Aucune modification de Yia n'est nécessaire pour accepter une nouvelle version
de Laravel, Symfony, Nuxt ou SvelteKit : `framework.version` n'est pas borné par
une liste. Le projet consommateur met simplement sa métadonnée à jour après la
migration de ses propres sources.

Introduire des bornes de versions compatibles constituerait un nouveau contrat.
Il faudrait d'abord le spécifier, choisir le comportement de validation et
ajouter les tests correspondants.

### Renommer l'identifiant ou changer son type

Renommer `nuxt` en une autre valeur, ou déplacer un framework de Node vers PHP,
invalide des fichiers `yia.yml` auparavant valides. Ce n'est pas une simple
édition de l'énumération : conformément à `docs/configuration.md`, il faut :

1. créer une nouvelle version de schéma ;
2. fournir le schéma dédié ;
3. définir une migration explicite ;
4. documenter cette migration.

Yia ne doit jamais convertir silencieusement le nom. Les tests doivent couvrir
l'ancien schéma, le nouveau schéma, la migration et l'erreur structurée en
l'absence de migration.

## Supprimer un framework

La suppression d'un identifiant accepté est également incompatible. Avant de
retirer sa valeur :

1. rechercher les spécifications, exemples, fixtures et tests qui l'utilisent ;
2. décider et documenter le chemin de migration des projets consommateurs ;
3. introduire la nouvelle version de schéma et sa migration explicite ;
4. retirer la valeur de l'énumération globale et de la contrainte par type dans
   ce nouveau schéma ;
5. adapter la normalisation, la documentation et les tests ;
6. vérifier qu'aucune source ni donnée d'un projet consommateur n'est supprimée.

Un projet qui déclare encore le framework retiré doit obtenir une erreur ou une
migration structurée, jamais une interprétation différente et silencieuse.

## Vérifier l'évolution

Depuis le dépôt Yia :

```bash
make test
make validate CONFIG=tests/projects/<fixture>/yia.yml
make generate CONFIG=tests/projects/<fixture>/yia.yml
make generate CONFIG=tests/projects/<fixture>/yia.yml
```

Vérifier en particulier :

- les configurations positives et négatives du schéma ;
- la stabilité de `YIA_CONFIG_INVALID` ;
- la valeur du framework dans le modèle normalisé ;
- sa présence dans
  `.agents/docs/architecture/development-environment.md` ;
- l'absence de changement Docker non spécifié ;
- l'idempotence du second passage de génération ;
- l'absence de secret et de modification des sources applicatives.

Les tests Docker end-to-end ne sont requis que si le nouveau framework introduit
réellement un comportement de runtime ou de routage. Une évolution purement
descriptive doit rester indépendante du code métier du framework.

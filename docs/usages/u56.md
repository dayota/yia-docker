# U56 — Ajouter, modifier ou supprimer une version PHP ou Node prise en charge par Yia

[← Index des cas d’usage](./index.md) · [Gestion du guide](../usages-management.md)

## Objectif

Faire évoluer, dans le dépôt Yia, le catalogue des versions PHP et Node que les
projets consommateurs peuvent déclarer. Contrairement au nom d'un framework,
une version de runtime possède une implémentation Docker complète.

Une version supportée doit être cohérente dans cinq couches :

1. le contrat normatif et le schéma de `yia.yml` ;
2. les constantes de validation des générateurs ;
3. le Dockerfile et ses outils épinglés ;
4. les artefacts Compose et les healthchecks ;
5. les tests, fixtures et exemples documentaires.

## Localiser le catalogue actuel

```text
docs/yia-spec.md
docs/configuration.md
docs/docker.md
schemas/yia.schema.json
src/yia/docker/php.py
src/yia/docker/node.py
src/yia/docker/compose.py
docker/php/<version>/Dockerfile
docker/node/<version>/Dockerfile
tests/unit/test_schema.py
tests/unit/test_php.py
tests/unit/test_node.py
tests/unit/test_compose.py
tests/integration/test_end_to_end_fixtures.py
tests/projects/
```

Le catalogue V1 contient PHP `8.2` et `8.4`, ainsi que Node `22` et `24`.
Les tuples `SUPPORTED_PHP_VERSIONS` et `SUPPORTED_NODE_VERSIONS` doivent rester
alignés sur les énumérations du schéma.

## Ajouter une version PHP

L'exemple suivant utilise PHP 8.5 à titre illustratif. La référence exacte de
l'image officielle et la compatibilité de Xdebug doivent être vérifiées au
moment de l'implémentation ; elles ne doivent jamais être devinées.

### 1. Mettre à jour le contrat et les tests

Ajouter PHP 8.5 aux listes normatives de `docs/configuration.md` et
`docs/docker.md`, avec l'image de base exacte et immuable retenue. Adapter les
énumérations ou exemples exhaustifs de `docs/yia-spec.md`.

Écrire avant l'implémentation des tests qui exigent :

- l'acceptation de `runtime.php: "8.5"` ;
- le rejet d'une version PHP inconnue ;
- la génération de `php/8.5/fpm-pools.conf` ;
- un service Compose `php-8.5` utilisant `8.5/Dockerfile` ;
- le tag `yia/php:8.5-<version-yia>` ;
- la conservation des volumes `vendor` et le routage FastCGI ;
- une image épinglée contenant Composer, les extensions attendues et Xdebug.

### 2. Étendre le schéma et le moteur

Dans `schemas/yia.schema.json` :

```diff
             "enum": [
               "8.2",
-              "8.4"
+              "8.4",
+              "8.5"
             ]
```

Dans `src/yia/docker/php.py` :

```diff
-SUPPORTED_PHP_VERSIONS = ("8.2", "8.4")
+SUPPORTED_PHP_VERSIONS = ("8.2", "8.4", "8.5")
```

Créer `docker/php/8.5/Dockerfile` à partir du contrat commun des images PHP, en
épinglant notamment :

- l'image officielle PHP-FPM ;
- l'image Composer ;
- la version de Xdebug compatible ;
- les mêmes extensions, outils, entrypoint et configurations partagées, sauf
  décision normative contraire.

Le contexte de build reste `docker/php/`, ce qui permet au Dockerfile de copier
`entrypoint.sh`, `xdebug.ini`, `default-pool.conf` et `global.conf`.

### 3. Ajouter une fixture représentative

```yaml
version: 1
project:
  name: php-next
environment:
  domain: php-next.localhost
applications:
  api:
    type: php
    path: apps/api
    runtime:
      php: "8.5"
    web:
      hostname: api.php-next.localhost
      public_directory: public
```

La fixture doit posséder son répertoire public. L'intégration Docker vérifie le
build, `php-fpm -t`, le healthcheck, la route HTTP et la version retournée par
`php --version`.

## Ajouter une version Node

L'ajout d'une version Node suit le même principe. Pour une nouvelle version
illustrative `26` :

```diff
             "enum": [
               "22",
-              "24"
+              "24",
+              "26"
             ]
```

```diff
-SUPPORTED_NODE_VERSIONS = ("22", "24")
+SUPPORTED_NODE_VERSIONS = ("22", "24", "26")
```

Créer `docker/node/26/Dockerfile` avec une base Debian officielle épinglée et
les outils imposés par `docs/docker.md` : `git`, OpenSSH, `gosu`, npm, pnpm et
Yarn. Conserver l'entrypoint non-root, `develop.sh`, le healthcheck et les règles
de lockfile.

Une fixture complète peut déclarer :

```yaml
version: 1
project:
  name: node-next
environment:
  domain: node-next.localhost
applications:
  frontend:
    type: node
    path: apps/frontend
    runtime:
      node: "26"
      package_manager: pnpm
    framework:
      name: nuxt
      version: 4
    web:
      hostname: node-next.localhost
      port: 3000
```

La fixture doit inclure un `package.json` valide avec un script `dev`. Les tests
contrôlent le service `node-26-frontend`, le tag
`yia/node:26-<version-yia>`, l'isolation de `node_modules`, les trois
gestionnaires de paquets, le healthcheck et le routage HTTP/WebSocket.

## Modifier l'implémentation d'une version existante

Mettre à jour une image de base épinglée sans changer l'identifiant logique, par
exemple conserver `runtime.php: "8.4"` tout en passant à une nouvelle image
corrective PHP 8.4, est une évolution compatible du catalogue.

Dans ce cas :

1. modifier le Dockerfile concerné ;
2. mettre à jour l'image exacte dans `docs/docker.md` ;
3. adapter `expected_bases` dans `tests/unit/test_php.py` ou
   `tests/unit/test_node.py` ;
4. reconstruire l'image sans cache si nécessaire pour prouver la reproductibilité ;
5. vérifier les extensions, gestionnaires, permissions, healthchecks et routes ;
6. publier l'évolution avec une version Yia appropriée.

Remplacer l'identifiant logique lui-même, par exemple `"8.4"` par `"8.5"`,
n'est pas une mise à jour corrective. Il faut ajouter la nouvelle version,
migrer explicitement les consommateurs, puis traiter l'ancienne comme une
suppression incompatible.

## Supprimer une version PHP ou Node

Retirer une valeur du schéma rend invalides des configurations auparavant
valides. La suppression exige donc, conformément à `docs/configuration.md` :

1. une nouvelle version de schéma ;
2. un schéma dédié ;
3. une migration explicite vers une version encore supportée ;
4. une documentation de migration.

Après définition de cette compatibilité, retirer de manière cohérente :

- la valeur du nouveau schéma ;
- `SUPPORTED_PHP_VERSIONS` ou `SUPPORTED_NODE_VERSIONS` ;
- le Dockerfile de la version lorsque sa période de support est terminée ;
- les attentes Compose et d'image devenues obsolètes ;
- les fixtures et exemples exhaustifs, en conservant les tests de migration ;
- les références normatives dans `docs/configuration.md` et `docs/docker.md`.

La migration modifie uniquement la configuration versionnée après décision
explicite. Elle ne supprime jamais les sources, `.env`, les volumes `vendor`,
`node_modules` ou les données persistantes. Un projet non migré doit recevoir
une erreur structurée plutôt qu'un runtime substitué silencieusement.

## Vérifier l'évolution

Exécuter d'abord la suite du moteur :

```bash
make test
make validate CONFIG=tests/projects/<fixture>/yia.yml
make generate CONFIG=tests/projects/<fixture>/yia.yml
make generate CONFIG=tests/projects/<fixture>/yia.yml
```

Avec Docker disponible, valider ensuite la fixture concernée :

```bash
YIA_RUN_DOCKER_INTEGRATION=1 \
  .venv/bin/python -m pytest -q tests/integration/test_end_to_end_fixtures.py
```

La Definition of Done exige :

- un schéma, les tuples Python et les Dockerfiles cohérents ;
- des images épinglées et reproductibles ;
- les services, tags et chemins de build attendus dans Compose ;
- des healthchecks et routes fonctionnels ;
- un second passage sans modification ni recréation inutile ;
- la préservation des sources et volumes ;
- des spécifications, fixtures et exemples synchronisés ;
- aucune valeur secrète dans les fichiers ou sorties.
